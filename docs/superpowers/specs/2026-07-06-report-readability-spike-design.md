# 工程 HTML 汇报可读性验证设计

## 目标

在继续投入 Linear 通知、发布 adapter、dashboard 接入之前，先证明 Symphony 生成的工程 HTML 汇报有可能达到人工可读要求。

本阶段不是做完整汇报系统，而是做一个 `readability spike`：

1. 准备少量真实或半真实的工程任务事实包。
2. 基于事实包生成可打开的 HTML 汇报样例。
3. 让用户直接审阅样例，而不是只看规则或流程描述。
4. 只有样例通过人工可读性验收，才继续做自动化流程。

如果样例不可读，后续流程暂停，优先迭代报告结构、叙事方式和证据呈现。

## 核心判断

自动规则只能守住下限，不能证明报告真的好读。

因此可读性验证必须分两层：

1. **规则下限**
   检查首屏摘要、异常区、证据索引、后续动作、长日志折叠、外部依赖等硬性结构。

2. **人工验收**
   用户打开报告后，判断它是否能在短时间内回答真正关心的问题。

规则检查通过但人工觉得不好读，视为失败。人工认可的样例才进入 golden report 样本库，作为后续生成器的目标形态。

## 验收问题

每份样例报告必须让用户在 1 到 3 分钟内回答：

1. 这批任务到底完成了什么？
2. 哪些结果可信，哪些结果不可信？
3. 哪些 issue 需要我介入？
4. 关键证据在哪里？
5. 还有哪些风险或未完成项？
6. 我是否愿意把这种报告作为 Symphony 自动运行后的默认汇报入口？

第 6 个问题是最终门槛。如果答案是否定的，不继续做配套流程。

## 样例范围

第一轮至少准备 3 类样例：

1. **正常完成的功能实现报告**
   用于验证报告是否能清楚说明做了什么、改了哪些模块、怎么验证、风险在哪里。

2. **批量 workflow 汇报**
   用于验证多 issue 矩阵、整体状态、异常置顶、证据导航是否好读。

3. **含失败或返工的批量汇报**
   用于验证 `failed`、`blocked`、`needs_rework`、证据缺失等情况是否会被优先呈现，而不是埋在表格里。

每类样例都应使用 `report_context.json` 驱动，避免报告作者直接编造事实。

## 输出协议

每个样例使用独立目录：

```text
.symphony/report-spikes/<sample-id>/
  report_context.json
  report_brief.json
  index.html
  summary.md
  manifest.json
  review.md
```

字段含义：

- `report_context.json`：事实包，只放任务、结果、证据、风险和链接。
- `report_brief.json`：报告设计说明，解释读者目标、报告范式、首屏信息和异常策略。
- `index.html`：人工审阅的主报告。
- `summary.md`：模拟 Linear/短摘要内容。
- `manifest.json`：生成时间、质量检查结果和文件路径。
- `review.md`：人工审阅记录，包含通过/不通过和修改建议。

## 人工审阅表

`review.md` 使用固定问题，避免只留下笼统反馈：

```markdown
# 汇报可读性审阅

样例：<sample-id>
审阅人：<name>
结论：pass / fail

## 快速判断
- 1 到 3 分钟内能否判断整体状态：是 / 否
- 是否清楚知道需要关注什么：是 / 否
- 是否清楚知道证据在哪里：是 / 否
- 是否愿意把它作为默认汇报入口：是 / 否

## 评分
- 首屏判断价值：1-5
- 结论清晰度：1-5
- 异常呈现：1-5
- 证据可追踪性：1-5
- 信息密度：1-5
- 视觉和排版：1-5

## 必须修改
- 无阻断项时填写“无”；否则逐条列出必须修改的问题。

## 可以后续优化
- 无建议时填写“无”；否则逐条列出非阻断优化建议。
```

通过条件：

1. `是否愿意把它作为默认汇报入口` 必须为 `是`。
2. 六个评分项不能有低于 4 分。
3. `必须修改` 中不能存在阻断项。

## 规则校验

规则校验用于防止明显不可读的报告进入人工审阅。

必需检查：

1. `index.html` 存在且非空。
2. 页面无外部脚本、样式、字体依赖。
3. 首屏区域包含整体状态、需要关注项和关键结论。
4. 所有异常 work item 出现在需要关注区域。
5. 所有关键结论附近有证据入口。
6. 长日志、长 diff、原始 JSON 默认折叠。
7. `summary.md` 足够短，可放入 Linear 评论。
8. `report_brief.json` 解释了为什么选择当前报告结构。

规则失败时可以保存 draft，但不进入人工验收。

## Spike 结束条件

`readability spike` 有三种结束状态：

1. **通过**
   至少 2 份样例通过人工审阅，且其中 1 份必须是含失败或返工的批量 workflow 汇报。通过样例进入 golden report 样本库。

2. **继续迭代**
   样例方向接近可接受，但存在明确修改项。继续调整报告范式和样例，不做配套流程。

3. **暂停汇报系统投入**
   样例多轮仍不能达到默认入口要求。暂停 Linear、发布、dashboard 等配套工作，重新评估是否值得继续做。

## 后续流程门禁

在 spike 通过前，不做这些事情：

1. Linear root issue 自动汇总评论。
2. 外部发布 adapter。
3. dashboard 报告嵌入。
4. 批量 workflow 自动通知。
5. 完整报告生成器产品化。

通过后，后续实现必须以通过的 golden report 为目标，不允许退回到“字段齐全但不好读”的模板输出。

## 已定决策

1. 先证明报告样例可读，再投入配套流程。
2. 自动规则只能守下限，人工审阅决定是否可作为默认入口。
3. 含失败或返工的批量 workflow 样例是必测项。
4. 通过样例成为 golden report，后续生成器以它为目标。
5. spike 未通过时，Linear、发布和 dashboard 工作暂停。
