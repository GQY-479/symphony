# 工程汇报设计范式 Spike

**日期：** 2026-07-13

**状态：** 已确认

**取代：** `2026-07-06-report-readability-spike-design.md` 及其实施计划

## 1. 决策摘要

Symphony 暂停把工程汇报实现为固定 Elixir renderer。当前阶段先验证“设计 Agent 能否针对具体工程任务选择合适的叙事和视觉形式”，再从人工认可的样例中反推专用 skill、输入协议和质量规则。

新的主路径是：

```text
受控事实包
  -> 设计范式探索
  -> 人工比较与选型
  -> golden report
  -> 反推专用 skill 和协议
  -> 自动生成与校验
```

`huashu-design` 在本阶段提供设计方法和能力参照，但不成为 Symphony 的生产运行时依赖。后续生产能力应沉淀为 Symphony 自己的工程汇报 skill。

## 2. 为什么需要重设方向

7 月 6 日的可读性方案已经做对了三件事：

1. HTML 是主要阅读面，Markdown 是短摘要面。
2. 正式通知前必须通过人工可读性门禁。
3. Linear、发布 adapter 和 dashboard 接入必须后置。

但原实施计划过早把 spike 变成了生成器工程：先固定 fixture、`report_brief.json` 章节、renderer 和 DOM 规则，再由生成结果充当待审样例。这样会让既有代码结构反过来限制报告形式，人工评审只能评价模板做得是否合格，无法发现工程汇报真正需要的叙事范式。

YQE-134 的 `huashu-design` 样例提供了反证。它没有沿用状态矩阵或 dashboard，而是根据案例中的状态冲突，把页面组织成判断优先的案件式 brief。虽然该样例还没有达到 golden 标准，但它证明了设计 Agent 在理解真实上下文后选择 form 的能力，可能比预先固定 renderer 更有价值。

因此，本阶段要验证的不是“某个 renderer 是否可读”，而是：

> Symphony 是否能建立一套让设计 Agent 从事实和读者任务出发，发现、比较并固化工程汇报范式的方法。

## 3. 目标

本阶段完成以下目标：

1. 用真实工程案例探索任务自适应的汇报形式。
2. 验证同一事实包在不同叙事结构下会产生哪些判断效率差异。
3. 验证候选范式能否迁移到不同类型的工程任务，而不是只适用于 YQE-134。
4. 形成经过人工认可的 golden report，而不是由当前 renderer 自行生成 golden。
5. 从 golden report 反推稳定的事实协议、设计 brief、专用 skill 工作流和质量下限。
6. 为后续自动化给出明确的进入门槛和失败回退路径。

## 4. 非目标

本阶段不做：

1. 生产级通用 renderer。
2. Linear 评论、通知或状态同步。
3. 外部发布、对象存储或 dashboard 嵌入。
4. 固定任务类型到固定 HTML 模板的映射。
5. 以 DOM 节点存在性代替人工可读性判断。
6. 把 `huashu-design` 安装状态或具体版本变成 Symphony 的运行前提。
7. 把现有三个 fixture renderer 输出直接升级为 golden report。
8. 在设计范式尚未稳定时实现完整质量评分器。

## 5. 核心原则

### 5.1 事实受控，形式开放

事实只能来自 `report_context.json` 和其中引用的可核查证据。设计 Agent 可以改变叙事顺序、信息层级、页面结构和视觉语言，但不能补写不存在的完成状态、测试结果、Git 事实或审查结论。

### 5.2 先设计，后抽象

先完成可比较的真实样例，再总结共同结构。不能先定义通用组件或 schema，再要求所有报告适配它。

### 5.3 同案多解，异案迁移

同一案例必须先做结构上真正不同的版本，才能比较 form 对判断效率的影响。候选 form 随后必须迁移到对照案例，证明它不是只对一个故事有效。

### 5.4 Golden 来自人工认可

自动生成成功、规则检查通过或视觉评分较高，都不能让样例自动成为 golden。只有用户愿意把它作为 Symphony 默认汇报入口时，样例才具备 golden 资格。

### 5.5 规则只固化已验证下限

质量规则在人工认可后提炼，只检查已经被样例证明稳定的下限。规则不能提前规定页面必须有哪些章节、卡片或 DOM id。

### 5.6 报告是判断工具，不是运行数据陈列面

报告首先帮助 workflow owner 判断完成度、可信度、介入点和下一步。状态、矩阵、时间线和日志只有在服务该判断时才进入正文。

## 6. 保留和重定义的 Artifact

### 6.1 `report_context.json`

继续保留，作为唯一事实输入层。它描述：

- 任务目标和成功条件；
- issue、review 和 workflow 结果；
- Git、测试、日志和 artifact 证据；
- 状态冲突、缺失证据和未解决风险；
- 可追溯的来源路径或链接。

页面布局、章节顺序、颜色、组件和视觉隐喻不进入该文件。

### 6.2 `report_brief.json`

继续保留文件名，但语义从“预先规定章节”调整为“可审计的设计判断”。至少记录：

```json
{
  "schema_version": 1,
  "case_id": "YQE-134",
  "audience": "workflow owner",
  "decision_to_enable": "判断 root 是否可信完成以及谁需要返工",
  "information_conflicts": [],
  "evidence_priorities": [],
  "narrative_hypothesis": "先揭示表面状态与审查结论的冲突",
  "form_rationale": "案件式 brief 让冲突、判断和证据链按阅读顺序出现",
  "visual_system": "编辑部式排版，低装饰，高证据密度",
  "discarded_alternatives": [],
  "assumptions": []
}
```

该文件不要求固定 `sections` 数组，也不作为 renderer 的页面配置。

### 6.3 `index.html`

仍是主要阅读 artifact。它必须自包含、可从本地文件系统打开，并根据具体任务选择叙事和视觉形式。

### 6.4 `summary.md`

仍是短同步面，只承载结论、需关注项、下一步和 HTML 入口，不复制完整报告。

### 6.5 `manifest.json`

继续记录输入、输出、生成方式和评审状态。设计阶段的状态使用：

- `draft`：技术上可打开，但尚未人工评审；
- `candidate`：进入对比评审；
- `accepted`：通过人工门禁，可成为 golden；
- `rejected`：不进入后续抽象，但保留失败原因。

## 7. Spike 流程

### 7.1 第一轮：同一冲突案例的三种 form

使用 YQE-134 作为种子案例，因为它同时存在 root `Done`、implementation 自报完成和 final review 要求返工，能够检验报告是否揭示表面状态与可信结论之间的冲突。

基于同一份事实包制作三个结构明显不同的版本：

1. **案件 brief**：情况、冲突、判断、证据链和所需动作。
2. **决策 memo**：需要做出的决定、候选解释、取舍依据和建议动作。
3. **审查叙事**：findings first、影响、证据、反证和修复条件。

三个版本必须保持事实一致，并至少在首屏构图、信息顺序和证据组织方式上存在结构差异。只换颜色、字体或卡片样式不算独立版本。

现有 `yqe-134-huashu` 样例作为案件 brief 的早期草稿进入第一轮，不自动视为 candidate 或 golden。

### 7.2 第二轮：迁移到两个对照案例

第一轮人工评审后，选择两个候选 form 或一个混合 form，迁移到两个真实对照案例：

1. 一个真正完成并有充分实现、测试和 Git 证据的功能任务。
2. 一个包含部分失败、阻塞或返工的批量 workflow。

对照案例必须使用真实运行事实。可以对敏感内容做脱敏，但不能用为了适配页面而编造的 fixture 事实代替。

### 7.3 第三轮：形成 golden 和设计语言

对通过评审的样例执行交叉复盘：

1. 哪些信息在所有任务中都必须出现；
2. 哪些结构只适合特定判断任务；
3. 哪些视觉约束提升了扫描效率；
4. 哪些证据呈现方式减少了来回核查；
5. 哪些自由度必须继续交给设计 Agent；
6. 哪些失败模式可以转成机械校验。

复盘结果用于编写后续 `engineering-html-report` skill 设计和实施计划，而不是回填到当前固定 renderer。

## 8. 设计 Agent 工作方法

设计 Agent 在生成每个版本前必须完成以下判断：

1. **读者任务**：读者打开报告后需要做什么决定；
2. **叙事角色**：该页面是结案说明、审查 brief、决策 memo、诊断记录还是批量态势说明；
3. **核心冲突**：表面状态、实现证据、审查结论和风险之间是否矛盾；
4. **证据优先级**：哪些证据直接决定结论，哪些只是背景；
5. **观众距离**：主要在笔记本本地阅读，同时保证窄屏可用；
6. **视觉温度**：根据任务选择冷静、警示、权威或克制，不默认使用统一主题；
7. **视觉母题**：form 必须从任务内容中生长，并在 `form_rationale` 中说明来源。

生成过程遵守以下约束：

- 使用真实内容，不用装饰性假数据填充页面；
- 优先展示判断和证据关系，不按字段完整度排列内容；
- 长日志、原始 JSON 和大段 diff 默认折叠；
- 关键结论附近提供证据入口和“该证据证明什么”的解释；
- 把假设、缺失证据和不确定性明确写出；
- 不使用 dashboard、卡片阵列或状态矩阵作为默认 form；
- 不追求跨任务统一视觉，先追求每个任务的表达准确性。

## 9. 人工评审门禁

每个 candidate 样例都必须让审阅者在 1 到 3 分钟内回答：

1. 真实结论是什么，而不是表面状态是什么；
2. 为什么这个结论可信；
3. 哪些证据最关键，去哪里核查；
4. 谁需要采取什么动作；
5. 还有什么不确定、缺失或风险；
6. 这种 form 是否适合该类任务；
7. 是否愿意把它作为 Symphony 自动运行后的默认汇报入口。

评审结果必须包含：

- `accepted` 或 `rejected`；
- 保留的设计判断；
- 阻断使用的问题；
- 可以迁移到其他案例的部分；
- 不应固化成规则的个案设计。

数值评分可以辅助比较，但不能替代上述结论。

## 10. Spike 通过条件

只有同时满足以下条件，才进入专用 skill 和自动化计划：

1. YQE-134 冲突案例至少有一个版本被人工接受；
2. 成功功能案例至少有一个迁移版本被人工接受；
3. 批量失败或返工案例至少有一个迁移版本被人工接受；
4. 三类样例的关键结论都能在 1 到 3 分钟内被正确复述；
5. 每条关键判断都有可核查证据，且没有事实编造；
6. 审阅者愿意把这些样例代表的能力作为默认汇报入口；
7. 能明确区分稳定协议、任务专属 form 和不应自动化的设计判断。

任一条件失败时，继续迭代设计范式，不恢复 renderer 扩展，也不进入 Linear、发布或 dashboard 集成。

## 11. 失败和异常处理

### 11.1 事实或证据不足

停止生成正式 candidate，把报告标为 `draft`，明确列出缺失事实。设计 Agent 不得用推断补齐完成状态或证据。

### 11.2 三个版本趋同

视为设计探索失败。重新选择叙事角色和信息顺序，直到版本具有结构差异，不能把换肤结果提交评审。

### 11.3 页面技术验证失败

HTML 无法本地打开、控制台报错、截图为空或窄屏发生重叠时，保持 `draft`，修复后才能进入人工评审。

### 11.4 样例视觉突出但判断效率低

人工门禁判定失败。视觉完成度不能抵消结论不清、证据难找或动作不明确。

### 11.5 候选 form 无法迁移

把该 form 记录为案例专属，不强行抽象为通用范式；继续测试其他候选 form。

## 12. 验证方法

### 12.1 事实验证

- 每个结论都能映射到 `report_context.json` 或其证据引用；
- 三个同案版本使用相同事实，不因设计方向改变结论；
- 缺失证据和冲突没有被页面措辞掩盖。

### 12.2 技术验证

- HTML 单文件自包含，无远程脚本、样式或字体依赖；
- 本地浏览器可以直接打开；
- 控制台没有页面错误；
- 桌面和窄屏截图非空、无明显重叠和截断；
- 锚点、折叠区和证据入口可以操作。

### 12.3 设计验证

- 三个第一轮版本结构明显不同；
- 首屏直接服务读者判断；
- 信息密度、排版和视觉层级适合工程审阅；
- 每个版本都能说明 form 从案例内容的哪里生长出来。

### 12.4 人工验证

- 记录 1 到 3 分钟阅读后的复述结果；
- 记录接受、混合、拒绝和返工原因；
- 只有人工接受的版本进入 golden 候选目录。

## 13. 输出目录

本地 spike 使用独立目录，避免与旧 renderer 样例混淆：

```text
.symphony/report-design-spike/
  yqe-134/
    report_context.json
    case-brief/
    decision-memo/
    review-narrative/
  feature-success/
    report_context.json
    candidate-01/
    candidate-02/
  workflow-rework/
    report_context.json
    candidate-01/
    candidate-02/
  review-index.html
```

第二轮只保留一个混合 form 时不创建 `candidate-02`。每个 form 目录固定包含：

```text
report_brief.json
index.html
summary.md
manifest.json
screenshot.png
review.md
```

`review-index.html` 只是对比和评审入口，不是生产 dashboard，也不代表最终汇报 form。

## 14. 现有草稿的处理

当前未提交的 `ReportSpike` Elixir 模块、Mix task、fixture 和三个 renderer 输出全部冻结：

1. 本阶段不继续修改；
2. 本阶段不提交；
3. 只作为旧方法的技术 baseline；
4. golden 形成后再判断其中哪些事实收集、文件写入或自包含校验能力可以复用；
5. 不复用其固定章节、HTML 结构或 DOM id 约束作为新方案前提。

现有 `yqe-134-huashu` 样例保留为设计探索种子，但用户评价仅为“勉强可看”，因此仍是草稿，不是 golden。

## 15. 后续生产架构假设

本 spike 通过后，预期生产链路是：

```text
Symphony 事实收集器
  -> report_context.json
  -> 工程汇报设计 Agent + engineering-html-report skill
  -> report_brief.json + index.html + summary.md
  -> 事实、技术和已验证下限校验
  -> 正式通知或发布入口
```

责任边界：

- Symphony 控制层负责事实收集、调用、保存、校验和通知门禁；
- 工程汇报设计 Agent 负责理解读者任务、选择 form 和生成页面；
- 专用 skill 固化方法、事实边界、验证步骤和已证明稳定的设计下限；
- 人工审阅负责 golden 接受和新范式的最终判断；
- `huashu-design` 作为探索来源和设计方法参照，不作为生产依赖。

这只是通过 spike 后的目标边界。当前阶段不实现该链路。

## 16. 已定决策

1. 汇报系统从 renderer-first 转为 design-agent-first。
2. 事实协议继续稳定，页面 form 在 spike 中保持开放。
3. `report_brief.json` 记录设计判断，不再预先规定固定章节。
4. 首轮先做 YQE-134 同案三解，再迁移到成功功能和返工 workflow。
5. Golden 必须来自人工认可，不能由当前 renderer 自举产生。
6. 质量规则后置，只固化人工认可后可证明稳定的下限。
7. 生产能力最终沉淀为 Symphony 专用 skill，不直接依赖通用 `huashu-design`。
8. 旧 Elixir pipeline 和 renderer 输出冻结为 baseline，本阶段不提交。
9. Spike 未通过前，不进入 Linear、发布、dashboard 或完整自动化集成。
